# Local OCR Ensemble Plan

## 1. Summary

Replace reliance on mixed OCR quality with a local ensemble of four meaningfully
different OCR channels (Tesseract + PaddleOCR, no external APIs):

1. `TesseractFullPage`
2. `TesseractLayoutCrops`
3. `PaddleLayoutCrops`
4. `PaddleTableRows`

Each channel produces its own normalized `ProcessingResult`. Reconcile only
after normalization, validate the final result strictly, save one final JSON, and
display that result.

## 2. Local OCR Only — No External API Providers

The ensemble uses only local engines: Tesseract and PaddleOCR. External API
providers (Adobe and others) are not part of the project: real PDFs showed noisy
names, duplicated players, and unreliable table mapping, and an external API must
not drive correctness decisions. Adobe and GLM-OCR have been fully removed; do not
reintroduce them.

PaddleOCR (`.venv-paddle`, 3.6.0) reads the small numeric cells and player rows
that Tesseract struggles with, providing a genuinely different reading rather than
correlated duplicate evidence.

## 3. Why Identical Tesseract Runs Are Useless

Running the same Tesseract command three times on the same image with identical
parameters creates correlated duplicate evidence, not an ensemble. Useful
strategies must differ in input region, preprocessing, page segmentation mode
(`PSM`), resolution, and parsing assumptions.

## 4. Shared Infrastructure

Reuse shared components where possible:

- PDF rendering;
- layout reference loading;
- crop preparation;
- image preprocessing primitives;
- Tesseract process execution;
- canonical entity key helpers;
- canonical stat key mapping;
- normalized `ProcessingResult`;
- validation and reconciliation services.

Do not create three unrelated Tesseract implementations.

Use a dedicated `pdf-structure/` folder for stable layout references, table
column definitions, expected headers, cell types, and documented FIBA regions.
Do not store generated OCR artifacts there.

`pdf-structure/` is the structural source of truth. Layout work must start from
its known FIBA contract:

- 15 Tier 1 and Tier 2 zones;
- macro and semantic crop roles;
- Home table before Away table;
- fixed player-table column order and headers;
- known stat mappings;
- known structural bottom rows: `Squadra/Allenatore`, then `Totali`.

Do not rediscover the whole page layout dynamically from OCR.

The generic active calibration helper is:

```text
python -m pdf_crop_runner.calibrate_layout
```

It consumes the canonical page image and OCR word boxes exported by
`TesseractFullPage`, starts from the fixed `pdf-structure/` template, and uses
rule-based geometry anchors to align known regions at runtime. It generates
corrected crops only when alignment evidence is reliable. It writes one
calibrated `crop-metadata.json` per document and does not run OCR.

## 5. Variant A: `TesseractFullPage`

Input: full rendered page.

Current state: complete active baseline. The existing Python full-page worker is
exposed as `TesseractFullPage`: it acquires the complete rendered page, runs
local Tesseract, writes raw diagnostics, maps to the canonical normalized
`ProcessingResult`, and preserves strategy provenance. This does not change the
final JSON schema or extracted-data behavior.

Purpose:

- broad baseline;
- competition and game metadata;
- teams;
- scoreboard;
- period scores;
- fallback text when zone strategies fail.

Suggested characteristics:

- stable full-page DPI;
- conservative grayscale and light contrast normalization;
- light sharpening only when measured helpful;
- page-oriented `PSM`;
- preserve text detail and punctuation.

Output: its own normalized `ProcessingResult`, not a raw-text shortcut.

It must not consume macro crops, semantic crops, table rows, or cells.

It also exports word boxes, bounding boxes, confidence, and a visual word
overlay. These are calibration inputs only. Scores, teams, players, totals, and
other extracted values must never be copied into `TesseractLayoutCrops`.

## 6. Variant B: `TesseractLayoutCrops`

Input: calibrated macro and semantic crops from stable layout references.

Current state: implemented as an independent diagnostic strategy. It consumes
all 15 Tier 1 and Tier 2 crops generated by `LayoutCalibration` from
`pdf-structure/layout-map.default.json`, runs local Tesseract on each complete
crop image, writes its own raw artifact, and emits a conservative partial
canonical `ProcessingResult`. It does not call `TesseractFullPage` internally,
does not copy full-page game data, and is not registered in the default UI flow
yet.

`LayoutCalibration` is deliberately bounded: fixed template plus runtime page
normalization, not a fully dynamic layout detector. The first implementation
uses the canonical full-page render as the coordinate frame, records rule-based
anchor matches, checks that expected structure remains aligned, and creates:

```text
runtime/Dataset/LayoutDebug/<document>.<short-hash>/full-page-word-boxes.json
runtime/Dataset/LayoutDebug/<document>.<short-hash>/full-page-word-overlay.png
runtime/Dataset/LayoutDebug/<document>.<short-hash>/crop-overlay-before.png
runtime/Dataset/LayoutDebug/<document>.<short-hash>/crop-overlay-after.png
runtime/Dataset/LayoutDebug/<document>.<short-hash>/layout-calibration-report.json
runtime/Dataset/LayoutDebug/<document>.<short-hash>/contact-sheet-after.html
```

Preparation is split into two operational tiers:

- Tier 1 macro crops: header, interval scores, main tables, bottom comparative;
- Tier 2 semantic crops: header parts, period intervals, home/away tables,
  team totals, and comparative tables.

Tier 3 row crops are future work and must build on the documented fixed table
structure rather than being introduced during crop-only preparation.

### Calibration Rules

Full-page geometry may be used only to:

- locate expected anchors;
- correct bounded offset and scale;
- align runtime rectangles for known zones;
- validate that the expected structure is where it should be.

It must not copy score, player, team-total, period, or comparative-stat values
into `TesseractLayoutCrops`.

The final-score crop starts from the known header region and uses team-name and
score anchors. It must not select period scores or interval scores as the final
score. The intended crop contains only or mostly:

```text
Miami Spritz 51 - 53 Saluta Andonio Spurs
```

Each player-table crop uses:

- the known column-header row as top anchor, included in the crop;
- Home table first, Away table second;
- `Squadra/Allenatore` and `Totali` as the final two structural rows and bottom
  anchors.

Visible player rows are variable: 7, 8, 9, or another valid count may occur.
Do not derive table boundaries from a hardcoded number of player rows.

If required anchors are missing, ambiguous, or inconsistent, calibration fails
closed. It must not silently emit apparently valid crops. The calibration report
must explain missing or ambiguous anchors, and `TesseractLayoutCrops` must not
consume uncalibrated or failed crops.

Useful regions:

- header;
- final score;
- period scores;
- home player table;
- away player table;
- home team totals;
- away team totals;
- comparative statistics when useful.

Suggested characteristics:

- reuse one render pass;
- crop-specific DPI or upscale where measured helpful;
- zone-specific preprocessing;
- suitable `PSM` per zone;
- conservative text handling for names;
- stronger numeric contrast only where safe.

This strategy must not call full-page OCR internally and return the full-page
normalized result. It must produce an independent normalized `ProcessingResult`.

The current mapper intentionally materializes only crop-level values that can be
parsed safely. Typed player-row extraction is the PaddleOCR row channel's job
(`PaddleTableRows`).

## 7. Channel 4: `PaddleTableRows`

Row-based player-table extraction using PaddleOCR native line detection on the
home/away player-table crops (`paddle_row_worker.py` + `paddle_row_parser.py`).

Input: player-table rows derived from the known FIBA table layout.

Expected columns:

```text
N.
Nome
Min.
FG
FG%
2P
2P%
3P
3P%
FT
FT%
RO
RD
RT
AS
PP
PR
SD
FF
FS
+/-
Val.
PTl
```

The printed points header may also appear as `PTI`, `PT1`, or `Ptl` after OCR.

Expected types:

- `N.`: jersey number, optionally prefixed by `*` starter marker;
- `Nome`: player text;
- `Min.`: `mm:ss` or `N.E.`;
- `FG`, `2P`, `3P`, `FT`: made/attempted ratio preserving `/`;
- percentage columns: decimal percentage;
- rebounds and other counters: integers;
- `+/-`: signed integer.

Typed OCR and parsing should differ by cell:

- preserve character detail for names;
- preserve `/` in ratios;
- preserve `:` in minutes;
- preserve sign in plus/minus;
- allow stronger thresholding for numeric cells only when measured useful;
- choose row/cell `PSM` settings appropriate to narrow regions.

Reject fake player rows:

- empty rows;
- numeric-only names;
- time values such as `18:13` used as names;
- `N.E.` used as a name;
- `Squadra/Allenatore`;
- `Totali`.

Map `Totali` to `team:Home` or `team:Away`, not to a player.

## 8. Strategy Independence

The three strategies should reduce correlated errors:

- full page sees broad context;
- crops isolate semantic regions;
- rows/cells use fixed geometry and typed parsing.

Vary DPI, preprocessing, and `PSM` only with a clear purpose. Do not multiply
configurations without measured value.

## 9. Normalized Output Contract

Every strategy produces the same normalized `ProcessingResult` contract before
reconciliation:

- canonical teams: `team:Home`, `team:Away`;
- canonical players: jersey, then name fallback, then row fallback;
- canonical stat keys;
- `PlayerStats.EntityId == StatValue.EntityId`;
- provider name;
- confidence;
- warnings;
- failed rules;
- raw/source provenance where useful.

Never reconcile raw OCR strings directly.

## 10. Reconciliation

Reconcile normalized outputs only.

Preserve:

- selected strategy;
- provider values;
- agreement;
- conflicts;
- confidence;
- warnings;
- source provenance;
- failed strategy evidence.

Do not silently drop conflicts. Agreement between three Tesseract strategies is
useful but still correlated evidence; strict mathematical and logical validation
remains decisive.

## 11. Provider Failure Handling

All three strategies should normally run. If one strategy fails:

- continue with usable strategies;
- preserve a visible warning and provenance;
- produce final JSON when enough reliable data exists;
- fail the overall flow only when no usable normalized result exists.

## 12. Parallelism

Sequential execution is acceptable first. Add parallelism only when:

- rendering is shared safely;
- each strategy writes to isolated paths or avoids diagnostics writes;
- no file collision or race exists;
- cancellation and error reporting remain clear.

Correctness comes before speed.

## 13. Runtime Artifacts

Normal mode should minimize writes:

```text
runtime/OutputJson/<final-json>
runtime/Working/        # temporary only
runtime/Logs/           # optional concise logs
```

Diagnostic mode may write:

```text
runtime/Diagnostics/
runtime/Diagnostics/RawOcr/
runtime/Diagnostics/Normalized/
runtime/Diagnostics/Crops/
runtime/Diagnostics/Reports/
```

Do not write raw OCR, crops, preprocessed images, provider reports, or
intermediate normalized JSON by default.

## 14. Final Validation and Viewer

After reconciliation:

1. run strict mathematical and logical validation;
2. apply only explicit safe derivations when needed;
3. validate again after derivation;
4. save one final JSON;
5. display final reconciled data in the result viewer.

The main viewer must not expose raw OCR or strategy comparison by default.

## 15. Incremental Implementation Order

1. Keep current stable Tesseract behavior as explicit `TesseractFullPage`.
2. Reuse shared rendering and layout preparation.
3. Measure and extend the independent normalized `TesseractLayoutCrops`
   diagnostic strategy without enabling automatic merge yet.
4. Add row-based typed player table extraction.
5. Add cell-based extraction only for fragile columns if needed.
6. Reconcile available normalized Tesseract strategies.
7. Measure correctness before adding parallel execution.
8. Reduce artifacts in normal mode after strategy outputs are stable.

## 16. Targeted Tests

### Full Page

- normalized `ProcessingResult` produced;
- canonical keys valid;
- player/stat entity IDs aligned.

### Layout Crops

- crop zones prepared or reused once from the fixed structure contract;
- anchor-based alignment fails closed when evidence is unreliable;
- score crop is not confused with period or interval scores;
- player-table crops include headers and use structural bottom anchors;
- independent normalized output;
- no full-page result masquerading as crop output.

### Rows / Cells

- expected columns parsed by type;
- `/`, `:`, and plus/minus sign preserved;
- fake player rows rejected;
- `Totali` mapped to team totals;
- `Squadra/Allenatore` ignored;
- duplicate jersey warning and fallback preserved.

### Reconciliation

- agreement preserved;
- conflicts preserve strategy values;
- failed strategy does not crash usable flow;
- final validation runs after reconciliation.

### Runtime

- original uploaded PDF preserved;
- temporary working files cleaned;
- normal mode avoids diagnostic artifact flood.
